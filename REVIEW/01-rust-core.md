# Rust core review — libre-cr v2

## Summary

Ship with fixes. The architectural seams (MCP framing, code-daemon client actor, supervisor, tool router, store) are well-designed and largely correct. However, three issues block v2 demos: the LLM providers don't correctly stream tool calls (so tool-use turns are broken end-to-end against real APIs), pairing the extension can't actually complete because no daemon route or IPC exists to issue redeemable codes, and `POST /v1/config` never persists, so any provider/key change is lost on restart. A handful of smaller correctness gaps (parallelism, cancellation-persistence, blocking I/O in async paths) round out the list.

## Critical issues (block v2)

**Anthropic provider drops streamed tool inputs** — `crates/libre-cr-review/src/provider/anthropic.rs:152-207`. `parse_anthropic_event` handles `content_block_start` (which contains an empty `input: {}` for `tool_use` blocks) and `content_block_delta` only for `text_delta` deltas. The real tool arguments arrive as `input_json_delta` deltas inside `content_block_delta` (and finalize at `content_block_stop`); the parser silently ignores them. As a result every Anthropic tool call enters the agent loop with `input == {}`, making `find_references`, `read_file`, etc. unusable. Fix: accumulate `input_json_delta` per `index` and emit `StreamEvent::ToolUse` at `content_block_stop` with the parsed JSON. Same class of bug in `crates/libre-cr-review/src/provider/openai_compat.rs:195-217` — each `tool_calls[i].function.arguments` chunk arrives as a partial-JSON string fragment that gets `serde_json::from_str` parsed in isolation, so all but trivial calls fail or are emitted multiple times with broken inputs. Both providers need a "buffer until block-end" stage before turning into `ToolUse`.

**Extension pairing cannot complete** — `crates/libre-cr-cli/src/pair.rs:17` and `crates/libre-cr-review/src/cli.rs:71-78`. `libre-cr pair` prints an 8-char code with `pair::generate()` that the daemon's `PairingStore` never sees; `libre-cr-review pair` constructs a *new* in-process `PairingStore`, calls `issue()`, prints the code, then exits — the running daemon's store is in a different process. There is no `POST /v1/pair/issue` (or any other) route on the daemon. Result: an extension can never present a code that `POST /v1/pair` will redeem with anything but 401. Fix: add a token-authenticated `POST /v1/pair/issue` returning a daemon-issued code, and have both CLIs hit it.

**`POST /v1/config` does not persist** — `crates/libre-cr-review/src/server/routes.rs:374-401`. The handler mutates the in-memory `ConfigStore` but never calls `Config::save`. After restart the provider kind/model/endpoint/`api_key_enc` revert to whatever's on disk (which is the default `kind = "mock"` if nothing was set there manually). This breaks the documented setup flow (extension opens `/config-ui`, user enters key, expects it to stick). Fix: persist after every accepted mutation; resolve `cfg_path` once at startup and pass it through `AppState`.

## Important issues (should fix before v2)

**`GET /v1/health` lies about the code daemon** — `crates/libre-cr-review/src/server/routes.rs:408-414`. The handler hardcodes `code_daemon: { connected: true, version: "mock" }` regardless of actual state. The spec contract is `{ ok, version, code_daemon: { connected, version } }`, and `health_code_daemon` already has the correct `health_hook` wiring — `/v1/health` should call the same hook (or share state).

**Tool calls within a turn are serialized, not parallelized** — `crates/libre-cr-review/src/agent/loop_.rs:269-294`. Spec § Agent Loop is explicit: "Tool calls within a single LLM turn run in parallel. A typical 'find callers and history' question results in 2-3 concurrent tool dispatches." The implementation `.await`s each `ctx.router.dispatch(&call)` in sequence. Fix: collect futures into a `JoinSet` / `futures::future::join_all`, then emit `tool_call`/`tool_result` frames as each resolves while preserving the eventual `ToolResult` block ordering for the next model turn.

**Cancelled turns are never persisted** — `crates/libre-cr-review/src/server/ws.rs:206-216`. The `tokio::select!` arm that loses to client disconnect simply discards the agent future; `agent::loop_::persist_cancelled` exists (and is marked `#[allow(dead_code)]`) but is never called. Spec § Concurrency and Cancellation says "Client closes WS → server aborts… all in-flight turns marked `cancelled`, transaction-committed." Fix: when the disconnect arm fires, persist the partial answer with `TurnStatus::Cancelled` before returning.

**`git fetch` and `git worktree add` block tokio workers** — `crates/libre-cr-code/src/repo/worktree.rs:66-103`. `WorktreeManager::prepare` is `async fn`, but the two `std::process::Command::output()` calls are synchronous and can be minutes long ("network-bound" per spec performance table). They block whichever runtime worker thread is poll-driving the future. `prepare_session` is called from the request-handling task tree. Fix: `tokio::process::Command` (or wrap in `spawn_blocking`); also `WorktreeManager::remove` and `evict` for symmetry.

**`ToolUse` from OpenAI emits per-fragment events with garbage args** — `crates/libre-cr-review/src/provider/openai_compat.rs:196-218`. Each streaming SSE chunk for a tool call carries a fragment of `arguments` (a JSON string built up piece-by-piece). The code attempts `serde_json::from_str(args).unwrap_or_else(...)` on each fragment in isolation and pushes a fresh `StreamEvent::ToolUse` per chunk, all with the same `id` and partial inputs. Also: `_tool_results` synthetic message produced by `build_body` is sent as a single non-API-shaped message rather than a sequence of `role:"tool"` messages — the API will reject it.

**WS reader-task select arm is structurally odd and leaks the inner spawn** — `crates/libre-cr-review/src/server/ws.rs:206-211`. `tokio::select!` is given `(&mut tokio::spawn(async move { reader_task.await; }))` — a freshly-spawned wrapper that already owns `reader_task`. The wrapper runs in the background, the select borrows its `JoinHandle`, and on the happy path (agent completes first) the wrapper is detached and its `JoinHandle` dropped — meaning the reader task keeps running with no one consuming presentation results until the WS frame writer fails. Replace with a straight `&mut reader_task` borrow and use `reader_task.abort()` after the select.

**Race between `next_ordinal` and `insert_turn`** — `crates/libre-cr-review/src/storage/store.rs:160-200`. The two methods acquire the connection mutex independently, so two parallel `POST /v1/sessions/:id/notes` (notes path is not single-flighted unlike `/ask`) will compute the same `ordinal` and one insert will fail the `UNIQUE(session_id, ordinal)` constraint. Fix: combine into a single `tx.transaction()` inside `create_note` / `insert_turn`, computing the max ordinal under the same lock as the insert. The same transaction should cover the FTS sync and tool-trace inserts; today a mid-batch failure leaves the turn row committed without its traces.

**Token comparison is not constant-time** — `crates/libre-cr-review/src/server/auth.rs:62-67`. `presented == expected` for the bearer token is short-circuiting. The token is 32 random bytes base64 so the practical attack is borderline, but the standard fix (`subtle::ConstantTimeEq`) is one line and the daemon already binds 127.0.0.1.

**`/v1/pair` is in `SKIP_AUTH_PATHS`** — `crates/libre-cr-review/src/server/auth.rs:14`. The redeem endpoint is intentionally pre-auth (you need to redeem before you have a token), but combined with the issue-side gap above, anyone on localhost can hammer it. Tighten by either rate-limiting per-IP/per-process or requiring a one-time URL hint shown by the daemon at issue time.

**Worktree single-flight map grows unbounded** — `crates/libre-cr-code/src/repo/worktree.rs:33-38`. `WorktreeManager::flight` inserts an `Arc<Mutex<()>>` per `(repo_id, ref)` and never removes entries. Long-lived daemons leak one per unique ref ever requested. Either evict after the guard drops (with a count of holders) or fold into the LRU eviction sweep.

**`Default` for `PairingStore` ships TTL = 0** — `crates/libre-cr-review/src/pairing.rs:11`. The derived `Default` sets `ttl = Duration::ZERO`, which makes every issued code instantly expire. Currently unused (all call sites use `new()`) but a footgun the next refactor will trip on. Either remove the `Default` derive or implement it manually to delegate to `new`.

**`libre-cr-code worktree.prepare` re-creates parent dirs but never re-fetches when the ref moves** — `crates/libre-cr-code/src/repo/worktree.rs:59-63`. Spec § Worktree management says "If the worktree exists, fetch + reset to the new FETCH_HEAD if the ref has moved (e.g., PR head force-pushed)." The implementation short-circuits on `wt_path.join(".git").exists()` and returns the existing path without comparing or refreshing. PR force-pushes will silently get reviewed against stale code. (`pr_diff_changed` in the review daemon flags the diff change, but the worktree is still the old commit.)

## Suggestions (nice to have)

**Stop hardcoding `repo_path: shellexpand::tilde` in tool inputs** — `crates/libre-cr-code/src/tools/fs_tools.rs:36-42` (and similar in `git_tools.rs`, `grep_tools.rs`, `repo_tools.rs`). Every tool runs `expand_path` on the caller-supplied `repo_path`. Either centralize via `ToolContext` (cheap) or delete it: the router injects `repo_path` from the worktree manager which is already absolute. Removes ~12 repeated boilerplate snippets and prevents drift.

**`Mutex<Connection>` for SQLite blocks the runtime under contention** — `crates/libre-cr-review/src/storage/store.rs:21` and `crates/libre-cr-code/src/repo/registry.rs:11`. Holding a `std::sync::Mutex` across .await is forbidden by `tokio` (the review daemon uses `tokio::sync::Mutex`, fine; the code daemon uses `std::sync::Mutex` in async tools, which can stall other tasks during inserts). Migrate the code-daemon side to `tokio::sync::Mutex` or wrap calls in `spawn_blocking`, or move to a connection pool (`r2d2_sqlite` / `deadpool-sqlite`).

**`build_router` swallows invalid extension origins** — `crates/libre-cr-review/src/server/routes.rs:52-65`. A malformed `extension_origin` falls back to `CorsLayer::very_permissive()`. Either error out at startup or quietly fall back to *no* CORS so a misconfigured field doesn't open the daemon to any origin.

**JSON schema validator is too lax** — `crates/libre-cr-code/src/tools/registry.rs:71-122`. Only top-level `required` and primitive `type` are checked; nested object schemas, `enum`, `items`, `minimum`, etc. are ignored. Several real schemas (`grep.glob`, `add_note.severity` enum, etc.) reach handlers unvalidated and become string parsing in the handler body. If swapping to `jsonschema` is too heavy, at least handle `enum` and `items: { type }` for arrays.

**`MockProvider` and `MockCodeDaemonClient` are wired into the binary, not gated** — `crates/libre-cr-review/src/cli.rs:108-115` falls back to the mock if `SpawnedClient::from_config` fails. In production this silently downgrades to fake answers. Make this an explicit opt-in config flag (and log loudly) so a misconfigured deployment surfaces immediately.

**`unsafe`-adjacent: `Mutex::lock().unwrap()` everywhere in code daemon** — `crates/libre-cr-code/src/repo/registry.rs:58,101,126,…`. Idiomatically fine, but a poisoned mutex (from a panic in another tool) will take the whole registry down on the next access. Use `lock().unwrap_or_else(|e| e.into_inner())` or upgrade to `parking_lot::Mutex` (no poisoning, faster).

**`git_show` doesn't separate `sha` from options** — `crates/libre-cr-code/src/git/show.rs:18-21`. Passing a sha-shaped string starting with `-` will be interpreted as an option. `git show -s --format=%an … "--" sha` would be safer.

**`ServerFrame::ToolResult { result_preview }` always carries the full result** — `crates/libre-cr-review/src/agent/loop_.rs:277`. The field is named "preview" but the entire `outcome.value` is shipped, defeating the spec's intent (the WS thinking trace should be a summary; full results live in the trace store). Either rename the field or actually truncate large payloads.

## Confirmed good

- `RestartBudget` (`crates/libre-cr-review/src/code_daemon/budget.rs`) — clean, well-tested sliding window. The `record()` vs `would_exceed()` separation is the right shape for the actor.
- `Actor::run` (`crates/libre-cr-review/src/code_daemon/client.rs:306-415`) — request multiplexing with id→oneshot map, exponential reconnect backoff with cap, fail_pending on EOF/write error so callers never hang.
- `unwrap_mcp_content` (`crates/libre-cr-review/src/code_daemon/client.rs:178-194`) — best-effort unwrap with pass-through fallback, and the tests cover all three branches.
- `safe_join` (`crates/libre-cr-code/src/util.rs:13-53`) — three-pass defense (absolute reject, lexical normalize, optional canonicalize-then-recheck) is the right call given symlinks. Tests cover absolute, `..`, and inside cases.
- `canonicalize_remote_url` (`crates/libre-cr-code/src/repo/remote_url.rs`) — handles the four common URL shapes plus userinfo stripping; thorough test coverage.
- `Supervisor::run` (`crates/libre-cr-cli/src/supervisor.rs:148-253`) — SIGTERM-then-SIGKILL with deadline, PID file lifecycle around spawn/exit, restart budget consulted on every restart attempt, clean test coverage for the three real outcomes.
- `Severity` derive(Ord) + `export_order` (`crates/libre-cr-review/src/storage/model.rs:72-121`) — the comment "Lowest precedence first so derive(Ord) reflects 'severer is greater'" is exactly the right discipline.
- `migrations.rs` — additive migrations only, per-migration transaction, "refuses to run newer schema" guard tested.
- `crypto.rs` — AES-GCM with a freshly randomized 12-byte nonce per encrypt, install key file persisted at 0600, round-trip and different-key tests in place.

## Coverage notes

Read end-to-end: `common/*`, `libre-cr-code/{mcp,tools,repo,git,search,util}`, `libre-cr-review/{agent,code_daemon,tools,storage,server,worktree,provider,pairing,error,config,cli,verbs}`, `libre-cr-cli/{supervisor,proc,pair,commands/start,commands/stop,logs}`. Spot-checked: `libre-cr-code/{languages,treesitter,config}`, `libre-cr-review/server/export.rs` end-to-end with tests, `libre-cr-cli/{doctor,update,paths}`. Not opened: `libre-cr-cli/src/{config,update}.rs` bodies (only their `commands/*` callers), `libre-cr-code/src/treesitter.rs` (Phase B stubs anyway per `tools/stubs.rs`), and integration test bodies beyond skimming names. The provider layer's Anthropic/OpenAI streaming is the area I'm most confident about being broken; the agent loop test suite uses `MockProvider` and so does not exercise real SSE parsing.
