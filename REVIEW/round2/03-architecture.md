# Architecture audit — libre-cr round 2

## Summary
Verdict: **sound-with-erosion-risks.** The two-daemon ownership split is implemented faithfully — the review daemon orchestrates worktrees purely through MCP calls, the code daemon contains zero PR/LLM knowledge, and the crate dependency graph matches the spec exactly. The genuine structural weaknesses are at the contract edges, not the core: HTTP response shapes are ad-hoc `json!` literals mirrored by hand in TypeScript, the error-code vocabulary is defined twice with one actual mismatch, `PROTOCOL_VERSION` is dead code, and GitHub is hardwired into the review daemon's storage layer where a platform adapter should sit.

## Boundary integrity findings
- **Review daemon never touches repo filesystems.** Worktree orchestration is pure MCP: `discover_repo` → `prepare_worktree` via the `CodeDaemonClient` trait (`crates/libre-cr-review/src/worktree.rs:128-203`); the resulting path is stored as an opaque string. The only exception is test-gated: `cfg.mock.code_intel` fabricates `/tmp/libre-cr-mock/...` paths (`crates/libre-cr-review/src/server/routes.rs:151-169`) — acceptable but it lives in the production handler.
- **Code daemon knows nothing about PRs.** A repo-wide grep finds PR strings only as opaque ref fixtures in tests (`crates/libre-cr-code/src/util.rs:159-170`). Every tool takes `repo_path`/`repo_id` (`crates/libre-cr-code/src/tools/`). Clean.
- **The GitHub PR-URL shape leaks into the review daemon's storage layer.** `parse_pr_url` hardcodes `/pull/<n>` and `pr_owner`/`pr_repo` columns (`crates/libre-cr-review/src/storage/store.rs:32-50`, `migrations.rs:18-21`), and `pr_inputs_from_pr_data` defaults to GitHub's `pull/<n>/head` pseudo-ref (`worktree.rs:241-245`). Platform identity belongs above the store.
- **Extension state exceeds the spec'd key set.** `specs/05-browser-extension.md:212-222` lists 5 keys; `extension/utils/daemon/storage.ts:14-28` declares 10. The extras are mostly UI ephemera, but `session.presentations_muted` and `ui.diff_change_dismissed` are *per-session* maps keyed by `session_id` — session state the spec says lives server-side (frames.ts:12-19 even documents that the daemon doesn't honor `mute_presentations` yet). Mild drift, growing.

## Dependency structure findings
- Crate graph is exactly per spec: `common` ← {`code`, `review`, `cli`}; `code` and `review` share only `common`; `cli` depends on neither daemon crate (it spawns binaries). Verified from all five `Cargo.toml`s.
- `libre-cr-e2e` dev-depends on `libre-cr-review` as a lib, importing `config::ScriptedEvent`, `provider::StreamEvent`, and `SpawnedClient` (`crates/libre-cr-e2e/tests/http_consumer.rs:636-637`, `spawned_smoke.rs:17-19`). This makes review-daemon *internals* a semi-public API: internal refactors now break the e2e crate's compile, and it tempts future tests to reach deeper. Contained risk (dev-dep only), but the mock-provider scripting types would be better promoted to a small test-support module with an explicit stability story.
- **Duplicated error vocabularies with a live mismatch.** `common::ErrorCategory` (`crates/libre-cr-common/src/error.rs:8-31`) and the code daemon's own `ErrorCode` (`crates/libre-cr-code/src/error.rs:9-17`) overlap by string convention only. `ErrorCode::InvalidInput` serializes as `"invalid_input"`, which exists in neither `ErrorCategory` (`"validation_failed"`) nor the extension's `ErrorCategory` union (`extension/utils/daemon/frames.ts:75-90`). A code-daemon validation error surfaced to the extension parses as an unknown category today.
- TS mirrors (`frames.ts` vs `ws_frames.rs`) match field-for-field on `ServerFrame`/`ClientFrame`/`AskInit`/`UsageTally`, with one forward-looking extra (`mute_presentations`). But `VerbDescriptor`, `SessionSummary`, `CreateSessionResponse`, `GetSessionResponse` (frames.ts:99-131) have **no Rust counterparts** — the daemon builds those bodies as untyped `json!` literals (routes.rs:189-220). That's the real drift surface.

## Protocol layering findings
- **WS frames: single source of truth, done right.** Defined once in `libre-cr-common/src/ws_frames.rs`, consumed by server (`ws.rs:14`), e2e, and a documented TS mirror with a runtime validator that drops unknown frames instead of crashing (`frames.ts:62-73`). This is the model the other two protocols should follow.
- **MCP envelope: convention, not contract.** The code daemon wraps results as `{content:[{type:"text",text:<json>}], isError}` (`crates/libre-cr-code/src/mcp/server.rs:170-179`) with `ensure_ok_envelope` (server.rs:189-197); the review client unwraps it best-effort (`code_daemon/client.rs:178-194`) and callers duck-type `.get("ok")` (`worktree.rs:155-158`). A non-JSON text part silently passes the raw wrapper through to the agent loop. No shared type for the `{ok, error?, message?}` tool envelope anywhere.
- `/v1/health` hardcodes `"code_daemon": {connected: true, version: "mock"}` (routes.rs:445-451) while `/v1/health/code-daemon` reports real state — two inconsistent health truths on adjacent routes.
- MCP handshake sends `protocolVersion: "2024-11-05"` (client.rs:208) and the server never validates it (server.rs:136).

## Growth-seam assessment
- **Phase C LSP backends: additive.** The `Tool` trait + registry (`crates/libre-cr-code/src/tools/registry.rs:13-18`) keys dispatch by name; stubs already register the final names and schemas (`stubs.rs`), so swapping a stub for an LSP-backed impl (or an impl that picks tree-sitter vs LSP internally per config/language) changes nothing wire-visible. There is no per-*call* backend selection mechanism, but none is needed at this seam.
- **Plugin verbs: minor surgery.** The catalog is `&'static` constants (`crates/libre-cr-review/src/verbs/mod.rs:51-58`), but the extension already consumes verbs dynamically via `GET /v1/verbs` → `VerbDescriptor`. Dynamic loading touches one file plus `&'static str` → `String` lifetimes. Good seam.
- **GitHub OAuth export: additive.** Export is a self-contained route (`server/export.rs`); a posting backend slots beside it.
- **GitLab/Bitbucket: moderate surgery, three layers.** Extension has no platform adapter — `utils/github/*` is imported directly by `ContentApp.tsx:7`, `SelectionLayer.tsx:5`, `content/index.ts:9`; plus the store-layer URL parsing and pseudo-ref defaults noted above. This is the weakest planned seam.
- **More presentation tools: additive but dual-listed.** `PRESENTATION_TOOL_NAMES` + schemas (`tools/presentation.rs:15-21`) and the extension handler registry must be updated in lockstep by hand; no contract test ties them together.

## Failure-matrix walkthrough
- **Code daemon dies mid-tool-call:** actor fails in-flight oneshots with `CodeDaemonUnavailable`, then reconnects with backoff under a per-hour budget (`code_daemon/client.rs:313-353, 395-407`). The router converts the error into `ToolOutcome{ok:false}` (`tools/router.rs:95-101`) fed back to the LLM — the turn survives. Matches spec.
- **Review daemon dies mid-WS-stream:** wrapper restarts within 5/60s (`cli/src/supervisor.rs:74-82, 220-251`); the in-flight turn is lost (turns persist at end-of-turn only); extension surfaces a connection error. Acceptable, spec-consistent.
- **Wrapper dies (SIGKILL):** `kill_on_drop` never runs → the review daemon survives *unsupervised*; the PID file holds the still-live review PID, so `libre-cr start` reports "already running" (`commands/start.rs:22-30`) and supervision is silently never re-established. Stale-PID handling for *dead* PIDs is correct; the live-orphan case isn't.
- **Review daemon SIGKILLed:** spawned code daemon sees stdin EOF and `run_stdio` exits (`mcp/server.rs:19-21`) — clean self-termination, no zombie path. Well designed.
- **Extension torn down mid-ask:** the WS reader task ends, the select arm persists the partial answer (`server/ws.rs:230-242`). Good.
- **No double supervision:** the wrapper spawns only `libre-cr-review` (`supervisor.rs:54-62`); the review daemon alone restarts the code daemon. Spec 08's topology holds.

## State ownership and version-skew findings
- Each datum has one writer — with one cross-owner cache: `sessions.worktree_path` is the review daemon's copy of a code-daemon-owned resource. The spec promises LRU eviction of worktrees; once eviction lands, `worktree_ready = worktree_path.is_some()` (routes.rs:148) will be true for a deleted directory and re-preparation is skipped. No invalidation channel exists.
- **Migration mechanisms are inconsistent.** Review: versioned, transactional, refuses newer schemas (`storage/migrations.rs:8, 88-92`). Code daemon: a single `CREATE IF NOT EXISTS` batch with a vestigial `migrations` table, no version gate, no forward-refusal (`repo/registry.rs:57-91`). The second real migration to the code registry will have to invent the discipline the review crate already has.
- **`PROTOCOL_VERSION` is never sent or checked** — defined and re-exported (`common/src/version.rs:5`) with zero other references in `crates/` or `extension/`. Nothing enforces the spec's minor-version wire-compat promise. Skew today degrades gracefully by accident: the extension drops unknown frames, serde ignores unknown fields. That's robustness, not versioning.

## Concurrency topology notes
- Review daemon: all `tokio::sync::Mutex` — `Store(Arc<Mutex<Connection>>)` (global DB serialization, fine at single-user QPS), `ConfigStore`, `busy_sessions`, `SessionStatusBoard`, `PendingCalls`, `WsSink`, client `schemas`/`health`. No nested cross-lock acquisitions found; no ordering hazard.
- **Single-flight-per-session can leak.** The session is inserted into `busy_sessions` before upgrade (`ws.rs:34-42`) and removed only inside the `on_upgrade` callback (`ws.rs:43-47`). If the client drops between the 101 response and upgrade completion, the callback never runs and the session is busy until daemon restart. Low probability, permanent effect; no TTL.
- The single-flight invariant lives in the *WS transport layer*, not a session manager — the Phase-4 MCP `ask_about_pr` path will bypass it unless deliberately routed through the same set.
- Code daemon: `std::sync::Mutex<Connection>` (`registry.rs:11`) and blocking gix/clone work execute directly on the async runtime. Harmless on serial stdio; in `mcp-socket` mode with concurrent connections (`server.rs:57-66`), a long `clone_repo` can stall the reactor. The per-key `FlightMap` for worktree prep (`repo/worktree.rs:14-33`) correctly enforces `worktree_busy`.

## Top erosion risks (ranked)
1. **Untyped HTTP response bodies + hand-mirrored TS types.** Next contributor edits a `json!` literal in routes.rs; `frames.ts` drifts silently. Prevent: define Rust response structs (serde) for every route and add a serialization contract test the TS types are generated from or checked against.
2. **Error-code string duality.** `invalid_input` already falls through the extension's category union. Prevent: have the code daemon emit `common::ErrorCategory` (it's the boundary crate's whole purpose) and delete `ErrorCode`.
3. **GitHub in the store layer.** Someone adding GitLab will be forced to widen `parse_pr_url` and the `pr_owner/pr_repo` columns under deadline. Prevent: a `platform` module owning URL→identity parsing and pseudo-ref construction, called by store/worktree, plus an extension `PlatformAdapter` interface over `utils/github/*` now, while there's one implementation.
4. **Single-flight at the transport, not the session manager.** The MCP server (Phase 4) is the documented second front door; `busy_sessions` won't guard it. Prevent: move the guard into a session-manager `ask` entry point both transports must call; fix the upgrade-failure leak with a drop-guard while there.
5. **`worktree_path` cache with no invalidation** — will become a live bug the day LRU eviction ships. Prevent: re-validate (idempotent `prepare_worktree`) on session open rather than trusting the stored path.
6. **Silent mock fallback in production `serve`** (`review/src/cli.rs:155-161`): if the code binary is missing, the daemon runs against `MockCodeDaemonClient` with only a log warning, and `/v1/health` claims connected. Easy for a contributor to ship a path bug that nobody notices.

## Confirmed sound
The ownership boundary itself is genuinely well executed — argument-shape discipline (`repo_path` vs `session_id`) holds everywhere I traced. The crate graph is minimal and acyclic. The supervision chain (wrapper→review→code) matches spec 08 with no double-supervision, and code-daemon orphan cleanup via stdin-EOF is elegant. The WS frame protocol is single-sourced with a defensive client parser. The MCP client actor (oneshot-per-call, fail-pending-on-disconnect, restart budget) is a solid pattern. The review store's migration discipline is exemplary. The `Tool` trait registry is exactly the right shape for Phase C.
